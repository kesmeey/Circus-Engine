# DC1／2／3 共用核心与兼容性边界

2026-10-27：0.5 加入独立 Dc2Host／Dc2Ui／Dc2Scene／Dc2Session 和 Android Dc2Activity，共用核心与资源层；DC2DM 原版系统和剧情的接入边界见 [DC2DM_PLAYBACK.md](DC2DM_PLAYBACK.md)。

2026-10-26 实施更新：0.4 原版模式已执行 START、WIN_SIZE、MAIN 和 SCESELECT，正式入口已移除 Android 路线选择与 MAIN 截获。原版按钮采用共用 UI 模型，进度和剩余缺口见 [DC3DD_ORIGINAL_UI.md](DC3DD_ORIGINAL_UI.md)。下面对 0.3 的描述保留为历史基线。

## 用户要求与最终验收目标（2026-10-26 修正）

用户需要可加载多部游戏原数据的兼容引擎，使用体验类似其提到的 krkr 模拟器：
从原版启动流程进入原版标题，使用原版开始／继续／存读档／设置／鉴赏等界面，再进入正文并返回标题。
标题、按钮、文字框、选择框和菜单流程属于引擎实现范围，不能由硬编码路线选择页代替。
通用 Android 外壳只提供游戏目录管理、平台权限和必要的输入映射。

0.3 产物是 DC3DD 专用剧情验证播放器，不满足这个目标：

- LauncherActivity 固定七条路线的 MES 名称与角色。
- GameActivity 固定使用 Dc3Resources / Dc3Host / DC3DD profile，正文框与选项由 Android 重画。
- Dc3Host.returnToTitle 截获 MAIN 转移，导致原版标题脚本没有执行。
- DC2DM 只有 framing 和资源分析基础，没有可执行的语义绑定和完整宿主。
- 本次只在自研 JVM 中检查原版入口，未启动 Windows 程序：MAIN 在 `0x2F5` 的 `23` 停止，START 在 `0x73` 的 `5E` 停止。它们是各自首个缺口，不是全部待实现清单；最终启动顺序还需遵循原程序生命周期。

已有封包、CRX、音频／影片、基础 MES VM、变量、跳转和快照继续复用。
“所有剧情路径能结束”保留为子系统验证，不能再作为完整游戏兼容的完成条件。

## 后续实施顺序

1. **原版系统流程优先。** 静态分析启动／MAIN／配置／存读档／鉴赏脚本，补注册按钮、热区、启用状态、悬停／按下态、延迟动作、菜单等待与脚本恢复。移除正式播放流程中的 MAIN 截获；路线直达仅保留作开发审计。
2. **原版画面与输入。** 按脚本和原资源绘制标题、文字框、选择框与菜单；统一逻辑画布坐标，将触摸映射到原按钮命中规则。原图背景加 Android 自制按钮不算完成原版 UI。
3. **从真实入口验收 DC3DD。** 全新数据目录进入原版标题，原版“开始”进入正常流程，原版菜单完成存读档、设置、鉴赏，再返回标题；通关标志和显示状态持久化。剧情、演出和媒体也要经过实际平台验证。
4. **DC2DM 验证复用。** 添加独立的版本语义与宿主差异，使用同一资源层、执行核心和原版 UI 系统，从其正常入口完成相同闭环。通过后才能称这两部受支持；不能仅凭识别到版本号就标记可玩。
5. **按引擎版本扩展 DC1／2／3。** 以已有样本逐组验证，维护“可识别／可解析／可进入原版标题／可玩／完整验收”的兼容表。未知版本明确拒绝，不借同系列名称推断兼容。范围继续排除 DC4／5。

运行时的目标组织为：游戏目录识别 → 版本绑定 → 通用 MES 执行与系统 UI／场景／音频等宿主模块 → Android 存储、绘制和输入输出。
版本差异要有明确绑定和证据，不假设全系列 opcode 或特殊变量布局一致。
原版 Windows 存档文件的二进制互通需独立验证；原版存读档界面和功能则属于本阶段必须补齐的体验。

## 既有实现与历史设计

0.3 已实现独立 `Dc3Host` 剧情宿主与 Android 播放器；最新接口职责、56 个 DD 绑定和跨脚本规则见
[DC3DD_RUNTIME_SEMANTICS.md](DC3DD_RUNTIME_SEMANTICS.md)。下面保留早期设计及其历史边界。

## 当前决定

Python 用于离线研究，Java 8 子集实现可在 JVM / Android ART 共用的核心，
Android 负责存储授权、绘制、触摸、音频和生命周期。选择 Java 的直接原因是可复用
本机已有 Android 工具链，并让同一套核心回归用例在桌面与 Android 运行。
未确认的宿主效果不会被空实现跳过；未知指令保留精确失败位置。

## 数据层接口

1. `GameIdentity`：数据指纹、MES profile、发行版标签、汉化配置。
2. `AssetLocation`：原文件、封包内偏移、长度、原始名称字节；允许按需读取。
3. `AssetCatalog`：名称目录与资源索引。保留未解析字段，不以猜测覆盖原值。
4. `MesFramingProfile`：头部布局、版本标识、参数范围、字符串字节变换。
5. `RawInstruction`：原始偏移、opcode、参数形状、原始字节。
6. `VersionSemantics`：版本 opcode 到稳定 semantic_id 的绑定；Java 核心执行已审查子集，宿主效果必须显式实现。
7. `CompoundRecord`：保留扩展参数、条件 companion、列表项、宿主字符串的上下文消费关系。
8. `StateContract`：逐版本描述变量的读取、写入、值变换、联动和宿主调用；原生地址只作证据。DD 的 bank 99 已有 83 个条目及默认规则。
9. `DeferredUiBinding`：按钮矩形、动作原始字节和激活时的潜在目标；与即时控制流分开。无法确定的动作继续保留。

格式 profile 与指令语义必须分离。`profiles/dc123.json` 只覆盖第 4 层，
不能把它当作执行指令映射，也不能把 26 个配置说成支持了 26 部游戏。
同一作品可能有多个格式配置；一些 DC1／2／3 发行版仍没有对应配置或样本。

## 静态分析已经证明的复用点

- DC3DD、DC2DM 的资源封包可由同一 PCK／CRM 读取器处理。
- 两作的 MES 都属于 offset2，但参数范围有差异。
- KTLEP 的旧 offset1 结构可以通过同一个参数解析器和另一份配置处理。
- 两作 NAMES.DAT 的记录布局一致，各表条目数不同。
- 汉化字符映射应是游戏配置的一部分，不能硬编码进字形渲染器。
- DC3DD / DC3WY 已共用变量、条件、标签与复合记录的静态分析器；详细原生地址见 [MES_SEMANTICS.md](MES_SEMANTICS.md)。
- opcode 差值不是常数，存储视图也因版本而异。PP 的大端变量视图不能从 DD 的小端参数布局推导。

## 仍需证明的内容

- 补齐 DC2DM / PP / 旧作的独立 native bindings，以及 DD / WY 尚未知的指令。
- 头部高位字段的完整业务意义、特殊变量副作用与存档生命周期。
- NAMES.DAT 附加数值的含义，以及脚本何时使用这些目录索引。
- 系统菜单是怎样执行、等待和处理输入的。
- 图像位置、差分混合、动画调度、音频循环和视频行为。

后续结合静态 PE 反汇编与明确授权的隔离副本轨迹。2026-10-26 用户授权 DC3DD 采集，
并指定正常启动文件。原游戏目录保持只读；轨迹只验证实际覆盖的路径，不自动推广到其他作品。

## 平台层

当前共用核心只依赖 `GameResources.Storage`、`MesVm.Library`、`MesVm.Host`，
Android 类型不会进入核心。时钟由宿主调用 `elapse` 推进；每轮执行有步数预算，
等待点击时不持续绘制。图像解码在工作线程，返回时检查会话代次，避免旧场景覆盖新场景。
保存使用带脚本哈希与校验和的 `CVS1`，先在新 VM/host 上验证，再发布恢复状态；
Android 用 AtomicFile 写入应用私有目录。大图和声音不进入无界全局缓存。

`GameResources` 的文件路径规范化与封包条目原始名称分开处理；CRXD/CRXJ 必须保留
封包上下文，不能仅凭解包后的文件名猜依赖。`NamesCatalog` 不擅自解释额外数值。

Android 的示例宿主 `DemoHost` 只实现原创测试场景。原作宿主必须依据证据补充，
不能直接把示例宿主当作 DC3DD 的完整状态机。

0.2 新增 `MesVm.FlowHost`：宿主可以在下一条指令被消费前提出显示等待，也可以在
当前指令后等待。`WAIT_HOST` 与原示例 `WAIT_CLICK` 独立；`TEXT_COMPLETE`、`ADVANCE`
是两个事件。事件票号保存在宿主状态中，Android 回调同时核对 VM 对象，旧画面的回调不会
推进新会话。取指预算耗尽不会丢掉上一条正文所要求的隐式边界。

`DialogueHost` 实现 DD 普通正文模块，`NativeText` 处理已确认的文本子集，
`TextCodec` 在 CP932 解码后应用外置 Unicode 替换，不修改资源名或跳转标签。
字符表指纹写入正文存档，配置变化时拒绝恢复。未实现的文本演出控制报告解码字节位置。
正文模块不接管特殊变量、初始化、语音、图像或脚本切换；原生编号的自制测试脚本与原作文件明确区分。

原 Windows EXE 导入的 DirectDraw／Direct3D 等 API 只是实现证据，不是移动端
必须复制的 API。不同游戏采用不同 Windows 绘图实现，不应因此分裂成两个 APK。

MES 读取/分发定位、第一版语义表和 WY 对照已完成。DD 已补特殊变量表、普通变量变更记录、
一条主 UI 回调路径和两种脚本切换的共同入口处理。接下来补待确认的 UI 路由、宿主效果和存档连接，
再向 DC2DM / PP / 旧作扩展。未确认的指令保持未知，
公共 switch 分支不自动解释为 NOP；分析出的边不是执行轨迹。
