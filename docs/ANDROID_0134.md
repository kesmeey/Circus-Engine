# Android 0.13.4：DC2PC 长 BGM 内存修复

安装 `build/distribution/circus-runtime-0.13.4-android-dev.apk`，直接覆盖安装，保留现有游戏配置、手机存档以及 0.13.3 的原版系统进度导入。

## 报错原因

用户报告的位置为 DC2PC Dacapo 线 `1ind_0120_e1_skr @0x244a`，异常为申请 47,314,256 字节失败，Java 堆上限 256 MiB。
该脚本前方的 `0x23ED` 播放第 42 首 BGM；`AdvData/music/042.PCM` 是未压缩 XPCM，包含 47,314,196 字节 PCM。
添加 44 字节 WAV 头和 Android 数组头后，恰好对应报错中的申请大小。

旧路径先将整个文件读入内存，复制出 PCM，再通过 `ByteArrayOutputStream` 构建和复制完整 WAV。
长曲与已有游戏画面、回看等状态叠加后，瞬时内存超出限制。该段 CG 为 800×600，并非异常大图。

## 修改

- 未压缩 XPCM（模式 0）与内嵌 Ogg（模式 5）通过 64 KiB 缓冲区写入播放缓存。
- Android SAF 连续读取使用同一个文件描述符，不为每块反复打开文件。
- 原版语音包使用有边界检查的条目视图，保持名称选择和分卷规则。
- 已解码音频直接写出，不再构建额外完整 WAV 副本；压缩模式 1／3 沿用原解码算法。
- MediaPlayer 按文件头识别音频；不改音质、采样率、声道、循环或存档格式，也不提高应用堆上限。

这次修复覆盖共同音频播放入口，未改动原游戏数据。DC2PC 本机 84 首 BGM 均为模式 0，均可使用有界复制路径。
压缩模式仍需解码缓冲区，本次不表示所有格式都已做到全程流式解码；也不表示所有内存热点已消除。

## 验证

- 本机原始第 42 首及最大第 43 首 BGM 的导出 WAV，与独立构造的 WAV 头加原 PCM 数据逐字节哈希一致，未改变音频内容。
- JVM 使用 `-Xmx256m` 并额外保留 130 MiB 占用：旧路径在 `Xpcm.wav() → ByteArrayOutputStream.toByteArray()` 溢出，新路径两首均通过。
- Android 15 模拟器实际 Java 堆上限为 192 MiB，并额外保留 130 MiB 占用：两首曲目导出通过；实际 `RuntimeActivity`／MediaPlayer 播放第 42 首、播放时钟推进及约 268.221 秒时长检查通过，随后连续推进 5 句对白。
- 671 项 JVM／Android ART 核心断言、47 项 Python 测试通过；Canvas 7 项像素约定和 484 项遮罩比较通过。
- DC3DD、DC2DM、DCPC、DC2PC 的 Android 启动、正文推进、回看、存读档和实际音频启动回归分别通过 21／25／27／25 项检查。

场景验证先执行原版 START 初始化，再通过审计入口直接进入报告脚本，执行至报错位置；此前媒体完成事件由测试模拟，报错处 BGM 使用实际 Android 播放器。没有声称完整重玩 Dacapo 线或完成用户实体手机验证。
证据位于本机 `build/android/verification-0134/`，不随源码发布原资源、原存档或测试剧情截图。
