# MES 指令语义：DC3DD 主样本与跨版本验证

**0.3 更新**：Android 已接入原作剧情，DD 运行时有 56 个数值绑定。
最新宿主规则与复用边界见 [DC3DD_RUNTIME_SEMANTICS.md](DC3DD_RUNTIME_SEMANTICS.md)，
测试范围见 [DC3DD_PLAYBACK.md](DC3DD_PLAYBACK.md)。以下 16／19 项、未分类记录计数和 0.2 限制是分阶段研究基线，
不表示当前 APK 仍只能运行测试场景。

分析日期：2026-10-26。前期使用静态读取、反汇编与 MES 解析；续轮经用户授权后采集了
DC3DD 隔离副本的真实轨迹。静态结论与动态覆盖范围分别说明。

本目录记录 **语义目录、复合记录、静态控制流及原生证据**。
Java 核心现已执行已审查子集，Android 测试场景已跑通；原作宿主效果仍不完整。
两份已验证配置各映射 16 个 opcode；其中脚本切换的完整副作用、UI 指令的显示行为仍标为 partial。
它们不是完整 VM，更不是两作的可玩兼容声明。DC3DD 仍有 204,540 个未分类的逻辑记录。

## 可复用的分层

```text
原 MES 字节
  → MesFramingProfile：保留物理记录、原始参数和文件偏移
  → VersionSemantics：opcode → 稳定的 semantic_id
  → 复合记录：扩展参数、条件 companion、求和项、UI 附属字符串
  → 静态注释和潜在控制流边
  → Java 共用 VM 子集 / Android 宿主（原作适配尚未完成）
```

机器可读表：`profiles/mes-semantics.json`。静态工具：`circus_tools/semantics.py`。
版本号不能简单相加减。例如 DC3DD→WY：变量赋值 `7C→78` 相差 4，命名跳转 `50→4D` 相差 3，块标记 `1F→1E` 相差 1。
同样的 `0x7C`，DD 是变量更新，WY 是条件比较。必须逐版本绑定，不能共用一张按数字索引的含义表。

## 第一版指令语义表

`p0..p3` 为四个有符号 16 位参数；短记录的两个参数为无符号字节。
表中语义以记录真正进入分发器为前提。被前一条指令消费时，其角色由复合记录规则决定。

| semantic_id | DD | WY | 已确认行为 / 边界 | DD handler 或直接证据 |
|---|---|---|---|---|
| `stream.stop` | 00 | 00 | 取指不前移，分发设置停止/让出标志；不是普通 NOP | `00438B21`, `0042AE49` |
| `control.marker` | 02 | 02 | 条件 companion / 求和结束；依上下文解释 | `0042D1B3`, `0042CF41` |
| `checkpoint` | 03 | 03 | 两字节合成编号，更新检查点状态、读取头部 u16 元数据；本身不跳转 | `004309B7` |
| `block.marker` | 1F | 1E | 第一字节非零时继续；为零时扫描下一个同 ID 块标记，并跳到其后 | `0042D228` |
| `label.named` | 47 | 44 | 零结尾字节串标签；搜索使用逐字节精确比较 | `00438750` |

DD 物理记录有 921 个 `7E`，复合后是 **125 条求和 + 796 个项**。

## 参数、PC 与头部规则

1. DD/WY 的代码缓冲区从 `4 + 6*N` 开始，包含三字节版本记录。初始 PC 为 3。
   对应文件偏移为 `version_offset + pc`；此前结构解析输出的 `offset` 一直是文件偏移。
2. `u16x4` 是磁盘参数形状名称；运行时通过 `cwde` 符号扩展，实际是 `i16x4`。
   例如 `FFFF` 是 `-1`，不是 `65535`。不修改 lossless 原始字节层。
3. DD 取指范围经原生验证：`00..38` 两字节参数；`39..43` 一字节加字符串；
   `44..62` 普通字符串；`63..67` 编码字符串；`68..FF` 四个 i16。
4. DD 编码字符串在 `00407B50` 逐字节 `+0x20 mod 256`，随后将解码后的 `$` (`24`) 改为空格 (`20`)。
   因而旧结构输出的加法字节结果不是完整原生文本处理结果。WY 的后处理在本轮仍保留未知。
5. 头部由 N 个 u32 和 N 个 u16 表组成。DD 原生检查点逻辑使用 u32 的符号位；u16 表被 `03` handler 按编号读取。
   屏蔽 bit31 后、以版本记录为基准得到的偏移在 DD 的 32,293 项和 WY 的 31,812 项中全落在指令边界。
   这是 **经过全量样本支持的偏移解释**，不等于已证明每项都是跳转表项，也不能据此宣称高位所有语义已解析。
   DD 其中 896 项并非“opcode03 且编号等于表索引”；保留原值，不能强改为标签。

## 条件与块跳转

DD 的 `80 bank,index,rhs,mode`：

```text
left = get(bank,index)
if mode 的低字节 bit7 为 1:
    right = get(rhs 算术右移8位, rhs & 255)
    compare_mode = mode & 127
else:
    right = rhs
    compare_mode = mode

compare_mode: 0 ==, 1 !=, 2 >, 3 <, 4 >=, 5 <=
block_id = sign_extend_i8(下一条三字节记录的第一个参数)
pc += 3
若比较为假：从当前 pc 扫描第一个 1F，其第二个参数 sign_extend_i8 后等于 block_id
找到后 pc = 标记记录起点 + 3
```

DD 的 9,335 个条件、WY 的 15,174 个条件，companion 均为 `02`。
原生 handler 本身直接读取后面的字节，没有验证 opcode；分析器将 `02` 作为已验证语法并在缺失时报告异常。
比较使用有符号关系。未知比较模式不补成任意布尔规则。

块 ID 决定匹配，不建立通常的花括号深度栈。比如 `1F 00 01` 会跳过后续部分，直到匹配 ID=1 的下一条块标记之后；`1F 01 01` 正常顺序通过。
扫描遇到 opcode00 仍没找到标记，原生进入错误分支；分析器记录 unresolved，不制造目标。

一个版本细节：WY 的块扫描器在 `0042F740` **符号扩展 opcode 字节**，DD 的对应代码使用零扩展。
WY 扫描到 `80..FF` 时会按负数走短记录分支，而不是统一按 9 字节跨过。
静态工具保留这个差异，并用人工样本测试。当前原始 WY 语料的已分析块扫描没有因此出现非法目标；是否以及如何兼容该原生行为，留到运行时设计，不擅自统一。

命名标签则从 PC=3 开始查找，区分大小写，精确匹配字节串；重名取第一项，跳到标签自身起点。DD 数字检查点另有搜索器 `00438820`，按 `03` 的两字节编号查找；当前未把它误命名为某条通用“数字跳转 opcode”。

## 变量存储规则

普通变量在 DD/WY 均为 11 组 × 100 字节，bank `0..10`，index `0..99`。
读取零扩展为整数，写入只保存低 8 位。因此普通变量 `255+1→0`，`0-1→255`。
DD 相对游戏状态对象的基址为 `+0x90C4`，WY 为 `+0x88A0`；这些原生偏移只作证据，移动端不照搬地址。

DD 的特殊 bank 不是上述数组的别名：

| bank | 原生读取 | 已确认写入范围/行为 | 状态 |
|---|---|---|---|
| `0x5D` | `+0x44DC + index*4` 的 32 位值 | index 0..19 | 槽位含义待确认 |
| `0x5E/0x5F` | 动态条目内、步长 40 的两个 32 位字段 | 有条目数量和 index=50 特例；0x5E 还存在特殊限值分支 | 需逐分支补全，不统一钳制 |
| `0x60` | `+0x174 + index` 的 u8 | 0..399 | 业务用途待确认 |
| `0x61` | `+0x304 + index` 的 u8 | 0..1199 | 业务用途待确认 |
| `0x62` | `+0x7B4 + index` 的 u8 | 0..649 | 业务用途待确认 |
| `0x63` | 按 index 分派至系统字段/函数 | 不是普通数组，写入可能触发副作用 | DD 已列 83 项及默认分支；宿主调用的业务意义仍部分未知 |
| `0x64` | `+0xCC + index` 的 u8 | 0..149；49 有额外调用，写入涉及状态更新 | 尚未完整建表 |

普通 bank/index 的原生检查只有部分上界检查，负数有越界风险；未来 VM 应显式诊断无效变量引用，不模拟对宿主内存的任意访问。
下文补充了普通变量的变更记录及重放路径；仍未依据地址位置猜测完整存档生命周期。

DC3PP 的对照揭示了真正的语义差异。样本 `DC3PP.exe` 的 SHA-256 为
`5474020ed4394df8d5a3b327f8aaa76e01926f59f7e0eb25b7ca33346201ad4c`。
变量读取函数 `004256A0` 还实现：

- bank 400：系统字节区内的相邻两字节，按 **大端有符号 16 位**组合。
- bank 300..310：普通 bank 减 300 后的字节区，两字节大端有符号 16 位视图，index 上界为 98。
- bank 200..210：bank 减 200 后的字节区，四字节大端组合视图，index 上界为 96。

这与 MES 指令参数的 **小端 i16** 是不同层次。DD/WY 的普通读取 fallback 不具有这些分支。
PP 的写入、完整 opcode 绑定尚未核对，故不能套用 DD profile；当前语义 CLI 对 PP 会拒绝给出已验证注释。

## 消除伪跳转：UI 附属字符串

DD `6C` 在 `0042B4DD..0042B569`，WY `69` 在 `00423B33..00423BBF`，都会读取 **后续记录起点+1 的字符串**，然后把 PC 前移 `strlen+2`。
即后续的 `50` / `4D` 在这里是字符串载荷，不会再次进入命名跳转 handler。

复合规则吸收 DD 的 544 条、WY 的 2,154 条字符串载荷后，之前出现的 223 / 202 个“找不到标签”全部消失。
这些实际是诸如 `:torisetu`、`:rapid` 的按钮字符串，不能当作损坏脚本或猜测成外部标签。
DD 的注册和一条主 UI 回调路径已静态确认，详见下文；其他 UI 上下文仍待追踪。

## 续轮：普通变量的变更记录与重放

`00403210` 同时查看 live `state+90C4` 和 shadow `state+9510`，各 1,100 字节：

```text
按 byte_index 从 0 到 1099 扫描：
    若 live[byte_index] != shadow[byte_index]：
        若 log_count < 1000：追加 (u16 byte_index, u8 live[byte_index])
        shadow[byte_index] = live[byte_index]  # 日志满时仍更新
```

日志计数在 `+8504`，索引数组在 `+8508`，新值数组在 `+8CD8`。
它记录的是**新值**，不能把条目倒序写回当成撤销。

`00403290(argument)` 先取 `n=argument & 0x7FFF`，把 live 和 shadow 都清零，
再顺序重放前 n 项到两份数组，最后令 `log_count=n`。n=0 也会清零并更新计数。
这个函数本身不检查 n 是否超过容量或索引是否越界；未来实现必须验证输入。
日志容量耗尽时也不能自行猜测成环形缓冲区。

`0040DD40` 是另一条清零两份数组的路径；主分发器 `0042B0AB` 在其第一个参数为 0 时调用它，
但这个 handler 还有其他行为，目前未把整条指令命名成单纯的 clear。
脚本切换的 `4B/4C` 会在不同条件下调用日志追加函数；此处没有证据支持“每次换脚本都清空普通变量”。
这些只是状态历史的一部分，尚不是完整存档格式或回溯系统实现。

## 续轮：UI 绑定与延迟控制流

`00417530` 保存四个矩形值和动作字节串。待登记的结构位于 UI 对象 `+D8`，大小 `0x298`；
四个值依次放入 `+D8/DC/E0/E4`，字符串放入 `+E8`。
已有待登记项时，函数先复制旧结构并加入列表，再初始化新项。
输入函数 `00415C60` 使用矩形字段进行位置处理；若干激活路径复制条目 `+10` 的动作到 UI 对象起始处，
并通过 `set(99,245,...)` 写入选择结果。

主 UI 的 `004339D5` 路径对非空结果调用 `00420C00`，按精确字节查找当前脚本标签。
